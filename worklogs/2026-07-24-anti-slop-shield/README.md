# Anti Slop Shield v1

**Status:** Complete (Phases 1–7; ready for human validation and merge)  
**Driver:** [QA-634 — Anti Slop Shield foundation and scenario model](https://linear.app/wasmer/issue/QA-634)  
**Related:** WARP-71; QA-541; QA-635 through QA-643; BE-666 (external dependency for backups)

## Objective

Turn hard-won Wasmer failure reproductions into portable, declarative scenarios. A scenario must support the investigation path from an experimental draft through a pinned local reproduction, then safely target dev, Bugtopia, and tightly constrained production validation.

Two reference outcomes anchor the work. The cross-Store WASIX panic, reproduced by `repros/WAX-600-edge-wasix-cross-store-panic.sh` until [`repros/wax-600/`](../../repros/wax-600) superseded it (D9, retired 2026-08-07; readable at commit `a1e41c1`), exercises pinning, environment perturbation, an existing-test workload, and an environment-log verdict. The WASIX timed-wait hang, reproduced by `repros/WAX-603-wasix-timed-waits-never-expire.sh` until [`repros/wax-603/`](../../repros/wax-603) superseded it entirely (D9 — local/native modes in Phase 4, remote modes in Phase 5; the script was retired 2026-08-10 and is readable in branch history), exercises a self-verdicting probe, a package-under-test component, multi-environment execution (local `wasmer run`, dev and prod Edge), a native-engine baseline run, and a first-class inconclusive outcome. The harness must replace everything both scripts do by hand with declarations and repeatable commands.

## Strategy and invariants

ASS belongs in this repository because it already owns `TestEnv`, the disposable local platform, Artillery, the Jest workloads, fixtures, and the `repros/` convention. The implementation lives under `ass/`; scenarios are checked in under `experiments/<slug>/` or `repros/<slug>/`. Slugs are lowercase on disk and resolve case-insensitively. `ass try` searches only `experiments/`; `ass run` searches only `repros/`; `ass list` presents their union with experimental entries marked.

Both commands use one scenario format, one execution engine, and one override surface (D12): `--env`, `--cpus`, `--executor`, and the generic `--component <name>=<selector>`, with `--edge` and `--backend` as sugar for the matching components. Drafts may additionally use floating component selectors in the declaration itself and omit a verdict. Persisted scenarios require concrete pins and a verdict; overriding any component selector on `ass run` switches the run's assessment to floating mode (D6) without touching the declaration. Because of that split, **anything that persists, pins, or reports a run reads the effective state, never the declaration** — the two diverge exactly at the override surface, and a consumer that reads the declaration silently attributes the run to versions it never used (review 4, R4-01). `ass promote` resolves a successful draft's floating selectors, moves it to `repros/`, and generates a provenance README. Drafts are committed collaboration artifacts but are never scheduled.

Components come in two kinds, and the split is invisible at the override surface. `edge` and `backend` are **platform** components: pinning one means booting the disposable stack. Everything else is a **package** component — a package under test that an executor consumes as `{{ component.<name> }}` and that never reaches docker compose. A scenario that declares no platform component, app fixture, perturbation or platform-log predicate therefore runs **without booting anything** (`ass run wax-603` is ~30s against ~6min); this is a correctness-neutral cost decision, but not making it would mean the harness is slower than the shell script it replaces, and people would keep the script. A load profile is named after the executor that runs it unless it names one with an inner `executor:` key, which is the only way to declare two profiles of the same executor — the shape a "compare two guest engine versions" control needs.

A scenario separates `fixtures`, `load`, and `verdict`. Fixtures finish before workload measurement and resolve to `ResolvedState`; app and probe fixtures may declare a `config:` block (open object; first member `max_instances`) that every target must honor or fail preflight (D13), because cross-request concurrency reproductions are structurally false-negative when requests spread across instances. Load may declare several executor profiles but exactly one is active per run (`executor:` names the default, `--executor` selects) and produces `RunOutcome`; verdict evaluates the common outcome and environment logs under explicit `any`/`all` combinators. A run ends `reproduced`, `not-reproduced`, `inconclusive`, or `setup-failed`; the optional `not_reproduced_when` block supplies the positive health proof separating not-reproduced from inconclusive, and declared control runs that violate their expected outcome also yield inconclusive. Scenario `meta` is typed and validated: `lifecycle` is a discriminated union (`open`, `fixed` with mandatory `fixed_in`/`fixed_at`/`evidence`, `retired` with `superseded_by`), and the run's exit code and pipeline alerting follow the assessment derived from lifecycle × pinned/floating mode, never the raw verdict fact (codes enumerated in D15). Nearly every Wasmer bug is a native-vs-guest engine divergence, so `verdict.baseline` — the native engine (`python3`, `node`, `go`, `cargo`, `binary`), an entry point, and an expected outcome — is required on persisted scenarios unless explicitly waived with a reason (D10); a violated baseline yields `inconclusive`, and a missing engine degrades capability without blocking the main load. Probes encode their result as a single `ASS-VERDICT:` marker line (D11) that the harness reads from typed channels — process/app-log capture or the HTTP response — with exit codes serving only as a consistency cross-check. The stable interfaces are:

```text
resolve(fixtures, targetEnv) -> ResolvedState
execute(load, ResolvedState) -> RunOutcome
report(scenario, ResolvedState, RunOutcome, verdict) -> JSON + summary
```

The target environment is a CLI or pipeline input, never scenario data. Local is disposable and is the only target where perturbations such as CPU caps and cache wipes take effect. Remote targets warn loudly and ignore perturbations. Production additionally requires `--i-know-this-is-prod`, interactive confirmation, and non-overridable executor caps; stress profiles reject production by default. Scenarios contain no secrets: remote identity comes from the existing `TestEnv` token flow or Doppler where required.

Use `TestEnv` helpers for all CLI calls and Edge HTTP so established registry, namespace, authentication, and local routing behavior remains intact. Prefer real local-platform and executor-boundary tests for observable behavior; unit-test parser, schema, and error branches. The final phase runs the mandated formatter and lint gates.
